# 版本规则

版本号形如 `大版本.小版本.补丁`（如 `0.4.2`）。

| 位 | 名称 | 什么时候加 |
|---|---|---|
| 第 1 位 | **大版本** | 有破坏性变更：老用户升级后行为/配置/数据需要处理，或整体定位改变 |
| 第 2 位 | **小版本** | 新增功能、新增可用能力，**老用法照旧** |
| 第 3 位 | **补丁** | 只修问题：bug、样式错位、文案、崩溃、安全修补，不新增功能 |

## 判定顺序

1. 用户升级后**必须做点什么**（改配置、迁数据、重新授权）→ 升**大版本**
2. 有**新功能**可用了，但升级后什么都不用改 → 升**小版本**
3. 只是**把已有功能修对**、没有任何新东西 → 升**补丁**

## 例子

| 改动 | 版本 |
|---|---|
| 修复输入框顶出容器 | 补丁 |
| 删掉已经失效的界面开关 | 补丁（不是功能删减，因为它本来就是坏的） |
| 新增「按实例设置自动重启次数」 | 小版本 |
| 删除可用的功能（比如移除某个已上线的主题） | 大版本 |
| 数据库表结构变更、配置项改名 | 大版本 |

## 每条发布的固定动作

1. 改 `backend/app/config.py` 的 `PANEL_VERSION` 与 `backend/app/__init__.py` 的 `__version__`
2. 在 `CHANGELOG.md` 顶部加一节（补丁写「修复」、小版本写「新增」、大版本写「破坏性变更」）
3. 打 `v大版本.小版本.补丁` 标签
4. **每次发布都新建一个发行版**，不复用旧发行版
5. 官网 `mc_packages` 与 `update_packages` 同步该版本，`/install_mc.sh` 指向新版本
